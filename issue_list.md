## 📑 ISSUE #1: [Backend] Support Date Range and Period Filtering for Overview Report

### Title
`feat(api): support date range and period filtering for admin overview report`

### Description
The current implementation of the Admin Overview Report API (`GET /api/admin/reports/overview`) is hardcoded to retrieve only the bookings created during the current calendar month. We need to upgrade this endpoint to support custom date ranges or predefined period filters (day, week, month, year) to show flexible revenue and booking trends.

### Current Behavior
- Code in `ReportService.cs`:
  ```csharp
  var now = DateTime.UtcNow;
  var startOfMonth = new DateTime(now.Year, now.Month, 1, 0, 0, 0, DateTimeKind.Utc);
  var bookings = await _context.Bookings
      .Where(b => b.CreatedAt >= startOfMonth && b.CreatedAt < startOfMonth.AddMonths(1))
      .ToListAsync();
  ```
- It only filters bookings within the current month, ignoring user input.

### Expected Behavior
- The API should accept query parameters for date filtering:
  - Option A: `[FromQuery] string filterType` (`day`, `week`, `month`, `year`)
  - Option B: `[FromQuery] DateTime? startDate` and `[FromQuery] DateTime? endDate`
- Filter the booking records dynamically based on the provided inputs.
- Calculate and group statistics (total bookings, completed bookings, failed bookings, cancelled bookings, revenue) mapped to the selected time range.

### Tasks Checklist
- [x] Add query parameters (`startDate`, `endDate`, `filterType`) to `GetOverview` action in `AdminReportController.cs`.
- [x] Update `IReportService` and `ReportService.GetOverviewReportAsync` signature to accept date inputs.
- [x] Implement query logic to filter bookings based on the parameters.
- [ ] Add unit tests in `ReportServiceTests.cs` to verify date range filter validity.

### Suggested Labels
`backend` | `enhancement` | `reporting`

## 📑 ISSUE #4: [Backend] Enforce Check-In and Status Validations for Emergency Stop API

### Title
`refactor(api): enforce check-in and status validations in Emergency Stop API`

### Description
The current implementation of the `EmergencyStopAsync` method in `AdminBookingService.cs` allows transitioning a booking to `Failed` regardless of its check-in state or historical status. To prevent operational errors, an emergency stop should only be triggered if the vehicle is currently checked-in and active (in progress).

### Current Behavior
```csharp
if (booking.Status == BookingStatus.Pending)
{
    booking.Status = BookingStatus.Failed;
    booking.CompletedAt = DateTime.UtcNow;
    await _context.SaveChangesAsync();
}
```
It accepts any `Pending` booking, even if `CheckInTime` is `null` (not started washing yet).

### Expected Behavior
The API should validate:
1. `booking.CheckInTime == null` -> Throw exception/bad request (cannot stop a booking that has not checked in/started).
2. `booking.Status != BookingStatus.Pending` -> Throw exception/bad request (cannot stop completed, cancelled, or already failed bookings).

### Tasks Checklist
- [x] Add validations in `EmergencyStopAsync` method inside `AdminBookingService.cs`.
- [x] Update error messages and return appropriate error codes (e.g. `BOOKING_NOT_STARTED`, `INVALID_STATUS`).
- [ ] Add unit tests in `AdminBookingServiceTests.cs` to cover these validation constraints.

### Suggested Labels
`backend` | `refactor` | `validation`
